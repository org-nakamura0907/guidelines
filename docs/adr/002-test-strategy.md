# ADR-002: テスト戦略

- **Status**: Accepted
- **Date**: 2026-07-19

---

## 背景

Astro + React 構成のドキュメントサイトにテストを導入するにあたり、何をどのレイヤーで検証するかを整理する必要がある。

対象となるテスト対象は大きく以下の2種類に分類できる。

| 種別                 | 例                                                     |
| -------------------- | ------------------------------------------------------ |
| React コンポーネント | Sidebar, TableOfContents, ThemeToggle 等               |
| ページ全体の動作     | ナビゲーション遷移, 検索, テーマ切替, アクセシビリティ |

## 決定

**Vitest (ユニット・コンポーネントテスト) + Playwright (E2E テスト)** の2層構成を採用する。

| ツール                          | 対象                                         | 環境                  |
| ------------------------------- | -------------------------------------------- | --------------------- |
| Vitest + @testing-library/react | React コンポーネントのロジック・レンダリング | jsdom                 |
| Playwright                      | ページ全体の動作・アクセシビリティ           | Chromium (実ブラウザ) |

## 理由

**Vitest を選んだ理由**

- Vite ベースのため Astro プロジェクトとの設定の親和性が高い (`getViteConfig`)
- `@testing-library/react` と組み合わせることでコンポーネントの振る舞いをテストできる
- カバレッジ計測 (`@vitest/coverage-v8`) まで一体で提供される

**Playwright を選んだ理由**

- ビルド後の実ブラウザで動作を検証できるため、Astro のサーバーサイドレンダリングや静的生成の挙動も含めて確認できる
- `@axe-core/playwright` との統合によりアクセシビリティ検証を E2E に組み込める
- Pagefind など「ビルド後に初めて動く機能」の検証は E2E でなければ不可能

**ユニットテストを書かないものの基準**

- `.astro` ファイル — Astro ランタイム依存のため jsdom では動作しない。E2E で代替
- `SearchModal` — `pagefind-ui.js` の動的インポートがテスト環境に存在しないため困難

## 影響

- **メリット**: コンポーネントレベルの高速なフィードバックと、実ブラウザによる統合検証を両立できる
- **デメリット**: E2E は `npm run build` が必要なため実行時間が長い。CI では週次実行ワークフローに分離する
- **中立**: `.astro` コンポーネントはユニットテストの対象外となるため、UI ロジックは React コンポーネントに切り出す設計が推奨される
